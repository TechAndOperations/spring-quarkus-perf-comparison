# Benchmark results — `spring-quarkus-perf-comparison`

Archive of the `metrics.json` files produced by `scripts/perf-lab/run-benchmarks.sh`.

The pipeline always writes to the same place (`/tmp/metrics.json` by default, via
`--output-dir`) and **overwrites the file on every run**. Results therefore survive only
until the next run — hence this archive.

## The benchmark suite

The project compares technology stacks on **one and the same application**: the `Fruit` /
`Store` / `Address` domain, an identical PostgreSQL database seeded with the same data, and
a single REST contract — `openapi.yml` at the root of the repo, which every module must
conform to. Load is generated by Hyperfoil against the `GET /fruits` endpoint, at a fixed
connection count.

Stacks measured: **Quarkus 3** (virtual and native), **Spring Boot 4** (virtual and native), **NestJS**, **Axum** (Rust) and **net/http** (Go).

**Every case is functionally equivalent.** They expose the same routes, the same status
codes and the same payloads; behavioural discrepancies found along the way — validation of
an empty name, the shape of a 404, the status of a POST — were explicitly aligned, and each
module's integration tests verify it.

The three non-JVM modules additionally offer a **"pure SQL" variant** alongside their ORM
path, selected via the `QUERY_MODE` variable: `go-sql`, `rust-sql` and `nodejs-sql` run a
hand-written query instead of going through GORM, SeaORM or TypeORM. **This variant does not
exist for the Java workloads** — Quarkus and Spring Boot are measured only through
Hibernate. An ORM-versus-raw-SQL comparison is therefore only possible for Go, Rust and
Node.

## Functional equivalence, implementation divergences

Equivalence is about observable behaviour, not about how it's reached. Three divergences
weigh on the numbers and should be kept in mind before any comparison.

### Data access

For the same `GET /fruits`, the number of round trips to PostgreSQL varies from one to
three.

| Stack | SQL queries | Strategy | L2 cache |
|---|---|---|---|
| TypeORM (`nodejs-orm`) | **1** | `find({ relations })` — a single join spanning the three tables, deduplicated in memory | no |
| SeaORM (`rust-orm`) | **2** | `fruit::find()`, then `find_also_related(store)`, which joins prices and stores | no |
| Hibernate (Quarkus, Spring) | **3 cold, 2 warm** | lazy collection loaded in a batch (`where fruit_id = any (?)`), then the stores | **yes** — `Store` is `@Cacheable` |
| GORM (`go-orm`) | **3** | `Preload("StorePrices.Store")` — one query per relationship level | no |

Hibernate is the only one with a second-level cache: after warmup, stores are served from
Caffeine and the third query disappears. That's a real and legitimate advantage under load,
but it has no equivalent in the other three ORMs.

All four counts are now **measured** — read off real traces in Tempo.

### Telemetry

Every module exports OTLP to the Grafana LGTM container's collector, but neither the same
signals nor the same depth.

| Stack | Traces | Spans / request | Metrics | Logs |
|---|---|---|---|---|
| `springboot4` | ✅ | 5 | ✅ 135 series | ✅ |
| `quarkus3-virtual` | ✅ | 4 (5 cold) | ✅ 132 series | ✅ |
| `nodejs` | ✅ | **10** | ✅ 109 series | ✅ |
| `rust` | ✅ | 4 | ✅ 28 series | ✅ |
| `go` | ✅ | 5 | ✅ 71 series | ✅ |

The span gap has narrowed a lot: Rust's four spans are the `axum-tracing-opentelemetry` HTTP
middleware span, the application span, and one `sea_orm.query_all` per query SeaORM issues
(two, from `sea-orm`'s own `tracing-spans` feature - no separate instrumentation crate). Go's
five and Node's ten still cover more ground (per-middleware spans, ORM-internal steps),
and Rust's metrics remain the shallowest in *kind*, not just count: its 28 series are Tokio
runtime gauges (worker count, queue depth, busy time) from
`opentelemetry-instrumentation-tokio`, not request- or database-level metrics like the other
stacks' 71-135. **The cost of observability is therefore still not fully comparable across
stacks**.

Getting Rust's metrics up to request/connection-pool depth would need `sqlx-otel` on the
`sql` path specifically (`QUERY_MODE=sql`, not the default `orm` one) - it cannot see the
`orm` path at all, since `SqlxPostgresConnector::from_sqlx_postgres_pool` takes a plain
`sqlx::PgPool` and SeaORM never calls `sqlx::Executor` on whatever pool object it's handed.

### ORM sophistication versus Hibernate

Hibernate serves as the reference: it's the richest functionally, and the other three fall
short along different axes.

| Capability | Hibernate | TypeORM | SeaORM | GORM |
|---|---|---|---|---|
| Relationship loading | tunable batch fetch | single join | join on to-one relations | one query per level |
| Second-level cache | ✅ Caffeine, per entity | ❌ | ❌ | ❌ |
| Persistence context, dirty checking | ✅ | partial | ❌ | ❌ |
| Embedded composite key | ✅ `@EmbeddedId` + `@MapsId` | worked around | worked around | worked around |
| ID generation | ✅ `@SequenceGenerator` | partial | manual | manual — explicit `nextval()` |
| Pagination over a joined collection | guarded, warned | unguarded | n/a | n/a |

None of the three offers an equivalent to `@EmbeddedId`: `StoreFruitPrice`'s composite key
is expressed everywhere as two columns marked as primary keys. None has a built-in sequence
generator, hence the manual call to `nextval()` on the Go and Rust side. And, above all,
none has a second-level cache — which alone explains the SQL-query gap observed under load.

These differences aren't flaws: each ORM applies its ecosystem's idiomatic default. They
simply mean the benchmark compares **applications with identical behaviour but different
internal work**.

### Warmup time

Just-in-time runtimes — the JVM for Quarkus and Spring, V8 for Node — don't serve their
first requests at the speed they will eventually reach. Code starts out interpreted, then
gets compiled in tiers; on HotSpot, only the switch to the C2 compiler delivers the final
steady state. GraalVM native images, Go and Rust have no such phase: their code is already
compiled at launch.

The pipeline accounts for this — 2 minutes of warmup, a 30-second pause, then 30 seconds of
measurement — but that mitigates the phenomenon without guaranteeing C2 has actually
finished. Two traces in this archive show it.

[PR #681](https://github.com/quarkusio/spring-quarkus-perf-comparison/pull/681) proposes an
improvement to the protocol on this point: confirming that the C2 phase has actually
finished before starting to measure, rather than assuming so from a fixed warmup duration.

### Cross-check against the upstream perf lab

The Quarkus perf lab publishes its own [throughput results](https://github.com/quarkusio/benchmarks/blob/main/images/spring-quarkus-perf-comparison/tuned/results-latest-tuned-throughput-for-all-light.svg#gh-light-mode-only)
for the same four Java runtimes, measured on dedicated hardware with 4 cores pinned to the
app — twice this archive's 2. Absolute numbers aren't comparable across that core-count
gap (see the caveat below), but the ratio to `quarkus3-virtual` (= 1) is:

| Runtime | This archive's ratio (2 cores) | Perf lab's ratio (4 cores) |
|---|---|---|
| quarkus3-virtual | 1.000 | 1.000 |
| quarkus3-native | 0.588 | 0.355 |
| spring4-virtual | 0.789 | 0.652 |
| spring4-native | 0.237 | 0.141 |

The ranking is identical, but every non-`quarkus3-virtual` runtime sits relatively closer
to it here than on the perf lab's dedicated hardware. One plausible reading:
`quarkus3-virtual`'s peak throughput is the most sensitive to a clean, non-virtualised
environment; the other three, already more constrained elsewhere (native build overhead,
Spring's own cost), have less headroom to lose and so degrade proportionally less under
this setup's added variance.

## Archiving a run

```sh
./archive.py                    # reads /tmp/metrics.json
./archive.py /path/to/metrics.json
```

The script names the file after the run itself — start timestamp, runtimes measured, memory
configuration and iteration count — then fills in the two tables below. It rejects aborted
runs (empty `results` section) and won't duplicate an already-archived run.

## Charts

Regenerated from the archived JSON files — rerun after every `archive.py`:

```sh
./density-ranking.py       # dots: each runtime's peak density
./startup-cost.py          # scatter: TTFR × RSS after the 1st request
./throughput-ranking.py    # bars: each runtime's peak throughput
```

Each script produces **one set per core count** found in the archive, suffixed `-2c` or
`-1c`. Runs at different core counts aren't comparable, so they don't share a chart.

All three share `_chartlib.py` — loading, scales, marks, palette. Colour carries the family
(Quarkus, Spring, non-JVM) and shape carries the execution mode: seven runtimes exceed the
three categorical slots the "all pairs" validation allows, hence this composite encoding.
Only the **ORM** path is plotted; the `-sql` variants answer a different question and stay
in the table.

### Column provenance

| Column | JSON key | Test required |
|---|---|---|
| Cores | `config.resources.app_cpus`, else counted from `config.resources.cpu.app` (`--cpus-app`) | — |
| `-Xmx` | `config.jvm.memory`, Quarkus and Spring runtimes only | — |
| Build | `build.avBuildTime` | always produced |
| TTFR | `startup.avStartTime` | `measure-time-to-first-request` |
| RSS 1st req | `rss.avFirstRequestRss` | `measure-rss` |
| RSS under load | `load.avMaxRss` | `run-load-test` |
| Throughput | `load.avThroughput` | `run-load-test` |
| Density | `load.maxThroughputDensity` | `run-load-test` |

A dash marks a test not selected in `--tests`. RSS **at startup** (`rss.avStartupRss`), the
native binary size (`build.native.binarySize`) and GraalVM's reflection counters aren't in
the table but remain in the archived JSON.

## Known caveats

- **Density inherits the memory budget.** It's a throughput/RSS-under-load ratio, so a
  generous `-Xmx` mechanically degrades it without the runtime being at fault.
- **This is not dedicated performance hardware.** Every run in this archive was executed
  on Ubuntu under WSL on Windows 11, itself a VM accessed over Citrix on VMware
  infrastructure with overprovisioning. Noisy-neighbour effects, host-level scheduling and
  the extra virtualisation layers all add variance this setup cannot isolate. The relative
  comparisons and trends should hold, but absolute numbers would benefit from re-running on
  dedicated performance infrastructure before being treated as conclusive.
- **The upstream perf lab's reference figures use 4 cores, this archive 2.** Absolute
  throughput therefore isn't comparable between the two; only the ratio to
  `quarkus3-virtual` within each dataset is, and even that should be read as a rough signal
  given the environment caveat above, not a precise measurement.
